# AppImage release packaging

Starting with v4.2.2, the Linux portable artifact is named `CF-Compass-<version>-x86_64.AppImage` (without the redundant `Linux` segment). The Debian package keeps its existing name. Existing published releases and links are not renamed.

The Linux release job first builds with electron-builder, then repacks the AppImage with a SHA-256-pinned, statically linked AppImage type-2 runtime and a zstd-compressed SquashFS payload. This removes the runtime's dependency on a system `libfuse2` library. It uses [appimagetool 1.9.1](https://github.com/AppImage/appimagetool/releases/tag/1.9.1) and [type2-runtime 20251108](https://github.com/AppImage/type2-runtime/releases/tag/20251108); both downloads must match the hashes in `scripts/repack-appimage.sh`. The bundled [mksquashfs build enables only zstd](https://github.com/AppImage/appimagetool/blob/1.9.1/ci/install-static-mksquashfs.sh), and the pinned runtime links libzstd. The verifier requires SquashFS compression ID 6 (zstd). The pinned runtime is a static PIE: its relocation table is valid, but an interpreter or a `DT_NEEDED` shared-library dependency is rejected.

The AppDir also contains `usr/share/metainfo/com.cfcompass.desktop.appdata.xml`, sourced from `build/com.cfcompass.desktop.appdata.xml`. Its component ID is `com.cfcompass.desktop`, and its launchable is checked against the actual root-level `cf-compass.desktop` file. `appstreamcli validate` must pass before repacking, and the final AppImage must extract an identical metadata file. After this explicit validation, appimagetool's automatic AppStream scan is disabled because it guesses filenames from the desktop entry and assumes a traditional system installation layout. Non-blocking standard metadata recommendations are retained in the build log.

The first/default AppStream screenshot is the English main workbench with built-in demonstration data, hosted at an immutable source-commit URL. The [catalog worker](https://github.com/AppImage/appimage.github.io/blob/master/code/worker.sh) uses the first AppStream screenshot for the listing when available. This supplies the requested listing image; it does not change CF Compass's built-in UI or claim that the image was captured on Linux. Runtime screenshots from the offline Ubuntu tests remain separate evidence.

Stable version tags from `Binah-Dev/cf-compass` also embed `gh-releases-zsync|Binah-Dev|cf-compass|latest|CF-Compass-*-x86_64.AppImage.zsync` and publish a matching `.AppImage.zsync` file. The updater is **external** (for example AppImageUpdate); this does not add automatic update checks to CF Compass. Ordinary non-release builds and prereleases do not advertise the stable update channel. A tag must match the packaged version. Existing sidecars cause repacking to stop, so use a clean build output instead of mixing packages from different builds.

To exercise the complete update-packaging path before publishing, manually run **Build and Release** on a test branch of the official repository with `appimage_stable_update_preview` enabled. This optional boolean input defaults to **false**. It sets `CF_COMPASS_APPIMAGE_STABLE_UPDATE_PREVIEW=1` for both repacking and final-artifact verification. The shared channel resolver rejects forks, non-manual events, tag refs, and prerelease version numbers in preview mode. Preview packages contain real stable-channel metadata and a validated `.zsync`, but remain workflow artifacts: the Release job explicitly excludes preview runs and still requires a version tag. Do not distribute preview artifacts as a published release; their metadata targets the public stable channel. This preview validates packaging and local reconstruction without requiring an initial public release or altering an existing one.

Before replacing electron-builder's output, `scripts/verify-appimage.mjs` checks the ELF runtime, type-2 marker, SquashFS payload, embedded update information, and the sidecar's filename, relative URL, length, SHA-1, and block-table length. Stable builds additionally reconstruct a copy with `zsync` using the complete local AppImage as a seed and compare the bytes. This validates the control file and block checksums; it is not a cross-version update against a live GitHub release. `SOURCE_DATE_EPOCH` defaults to the source commit's timestamp and normalizes SquashFS/zsync timestamps; this is not a claim that the entire electron-builder build is byte-for-byte reproducible.

The packaged Electron application still uses the host's C library and may require other ordinary Linux desktop facilities, including a working FUSE device and `fusermount` helper for mounted execution. Repacking does not make it universally compatible with every distribution.

The generated AppRun launcher is adjusted to preserve Chromium sandboxing. electron-builder 26.15.3 otherwise adds `--no-sandbox` whenever its `unshare -Ur true` probe fails. `scripts/prepare-appimage-launcher.mjs` removes only that automatic fallback and preserves the remaining generated environment, license handling, and argument forwarding. The desktop entry must also omit sandbox-disabling arguments. Changed upstream launcher templates fail explicitly for review, and the final AppImage's launcher and desktop entry are extracted and compared. Hosts that restrict Chromium's sandbox prerequisites may still refuse to launch; the package does not silently turn sandboxing off to hide that restriction.

The release workflow tests the **installed Debian package** on pinned Ubuntu 24.04, including its generated application-specific AppArmor profile. It then tests the **final repacked AppImage** on Ubuntu 24.04 and Ubuntu 22.04. On restricted Ubuntu 24.04, the identical AppImage is installed root-owned at `/opt/cf-compass/CF-Compass.AppImage` and given the exact-path user-namespace permission described in [the installation guide](linux-appimage.md). Ubuntu 22.04 tests the portable artifact without that extra profile. Both AppImage environments must pass normal FUSE-mounted launch and `APPIMAGE_EXTRACT_AND_RUN=1` launch. This is conditional support for the documented installation methods, not a claim that an unconfigured restricted host can run the AppImage from an arbitrary path.

The first-launch script checks the application's actual mount/extraction path, creates a fresh temporary profile without account/cache fixtures, and verifies the built-in demo workbench, search, favorites, navigation, and minimum window size. It also checks the renderer's sandbox preference, seccomp filter and no-new-privileges status. On the restricted runner, the expected AppArmor label must be attached, the renderer must use a separate user namespace, the global restriction must remain enabled, and an unrelated namespace probe must still be denied. The exact-path permission is an explicit application-specific host-policy exception, not a full AppArmor confinement policy. The application never loads this policy or requests elevated rights itself. Evidence is saved as workflow artifacts, not Release downloads.

Once Linux repacking and package verification succeed, that build artifact is retained even if a later startup check fails. Ubuntu 22.04 can therefore independently diagnose the same package after the current runner fails. Within each runner, a failed FUSE or extraction check does not prevent collecting evidence from the other mode; the step still fails if either check fails. Windows and macOS package artifacts remain success-only. Artifact retention does not relax publication: the Release job still requires the packaging job and Ubuntu 22.04 verification to succeed, as well as a non-preview version-tag build.

Each AppImage first-launch test runs in a temporary network namespace with only loopback enabled, so both Electron's main process and renderer are offline while Playwright can still connect locally. The application runs as the ordinary runner user. Missing `/dev/fuse` access or unavailable network isolation fails the gate instead of silently replacing mounted testing with extraction. This setup does not change the host network configuration. Other distributions still need their own compatibility checks.

Local verifier tests on Windows (`node --test scripts/test-appimage-release.mjs`) and separate Bash/YAML syntax checks cannot demonstrate AppImage startup. The historical [cloud run 36423559190](https://github.com/Binah-Dev/cf-compass/actions/runs/36423559190) verified the 4.2.1 test package on Ubuntu 22.04 but failed on restricted Ubuntu 24.04.5 without per-application authorization. That failure is retained as evidence; the v4.2.2 candidate must independently pass the documented installation and sandbox checks. See `docs/appimage-acceptance.md` for dated coverage and results. After publishing the first update-enabled stable version, separately check its public sidecar. A real cross-version update against GitHub requires a later stable release and is not established by local seed reconstruction.

The CI release job compares downloaded assets against a private SHA-256 manifest generated from the build artifacts. Neither per-package `.sha256` files nor `SHA256SUMS.txt` are published. The `.zsync` sidecar remains public because external AppImage update tools need it. The v4.2.1 download retains its original name and runtime; the new runtime, naming and update metadata start with v4.2.2.

`scripts/verify-release-assets.mjs` requires the exact six platform filenames for the package version, plus exactly one matching `.AppImage.zsync` for a stable release. Empty files, missing platforms, old sidecars, checksum attachments, and any other unexpected entries stop publication. The same inventory is checked again after downloading the draft Release.
